The Factory That Writes Code While You Sleep

AI agents can now write software faster than anyone can review it. The people getting the most out of them have stopped asking agents to code and started building factories around them.

A plain-language guide, with a small working factory as the example. November 2026.

On a Tuesday afternoon in November, two AI agents started work on the same small codebase at the same second. One was asked to add a function that checks whether a piece of text is a valid web address slug. The other was asked to add a function that turns a slug back into words. Neither knew the other existed.

Both did what a person would do. They added their new function to the bottom of the same file, and their test to the bottom of the same test file. The second agent finished first, and its work went straight into the main copy of the project. When the first agent finished a minute later, its work no longer fit. The two changes had collided.

What happened next is the interesting part. Nobody was paged. A script noticed the collision, refused to merge the work, and sent it back to the agent that wrote it with a one-line note: conflict in these two files. On its next pass, that agent pulled in the other agent's change, kept both functions, and tried again. This time it went in. Seconds later a second script ran the full test suite on the result, and a third AI read the change looking for bugs. It found none.

Total human involvement after writing the two task descriptions: zero.

That is a software factory, in miniature. It is also the clearest way to understand why people who build software with AI are talking less about prompts and more about plumbing.

The problem nobody expected

For the last couple of years, the story of AI coding has been about the writing. Can the model write a function? A feature? A whole app? That question is mostly settled. Current agents write plausible code quickly and cheaply, and you can run several at once.

Which creates a new problem. If five agents each produce a change every few minutes, someone has to decide which of those changes are safe to keep, in what order, and what happens when two of them disagree. If that someone is you, you have not hired a team of tireless engineers. You have pointed a firehose at your inbox.

Kit Langton, who works on the open-source coding agent opencode, posted a short video in November 2026 of the system he built to cope. It was labelled "LIVE - RUNNING TONIGHT". It had landed 50 changes that day. And almost none of it was about getting the AI to write code. It was about what happens after the AI says it is done.

Once machines write the code, the hard part moves to getting their work into one place without breaking it.

So what is a software factory?

The simplest definition: a software factory is a codebase where people stop writing the changes and start writing the rules for which changes are allowed in.

Agents do the typing. Humans write three things instead: the tasks, the checks that prove a task is finished, and the order of operations for getting finished work into the project.

There is an easy test for whether you have one. Close your laptop tonight. If a working, tested change still lands in your project by morning, and the project still works, you have a factory. If nothing happens until you come back and click things, you have a very fast tool. Running five agent windows side by side is not a factory. It is a busy person.

What is inside one

Every factory has the same handful of parts. The easiest way to picture them is a restaurant kitchen during dinner service, because a kitchen already solved this problem: many people working in parallel, one pass where finished plates leave, and no tolerance for sending out something wrong.

The ticket: a task with a finish line

Nobody in a kitchen cooks without a ticket. In a factory, no agent works without a task, and the most important line on the task is how you will know it is done. Not "improve the signup page." Something a machine can check.

Why
An agent with no finish line will tell you it finished. It is not lying, exactly. It just has nothing to measure against. A command that fails today and passes tomorrow is the only kind of "done" you can trust from something that never tires of saying yes.

The cooks: one agent, one task, one workspace

Each agent, called a builder, gets one task and its own private copy of the project. It cannot see what the others are doing and cannot overwrite their files.

Why
Two cooks sharing one cutting board will eventually chop each other's onions. It is far easier to give everyone their own board than to make them coordinate. The whole design leans on this idea: remove the sharing instead of managing it.

The quick taste: a check before anything is accepted

Before a builder hands its work in, the factory runs a short set of checks. Does the code still make sense to the computer? Do the tests nearest the change pass? Is anything obviously broken left behind? Formatting, the dull rules about spacing, is never a reason to reject work. The factory just fixes it and moves on.

Why
The check has to be quick, because everything waits on it. And it has to be a script, not a line in the prompt. Tell an agent "don't leave debugging code behind" and it usually won't. Write a script that rejects any change containing it, and it never will. A rule in a prompt is a suggestion. A rule in a script is a law.

The pass: one person decides what leaves the kitchen

This is the heart of the factory, and the part most people skip. In a restaurant, every plate goes past one person at the pass. In a factory, that person is a script called the integrator, and it is the only thing allowed to change the main copy of the project. It takes finished work one piece at a time: merge it with the latest version, run the quick checks again on the combined result, and only then save it. Kit's takes one to seven minutes per change.

Why one at a time
Taking turns sounds slow, but it means every version of the project that ever existed was actually tested. We built exactly this trap into our own factory's test, and the integrator caught it.

Why rejected work goes back to its author
When two changes collide, the agent that wrote the second one is the only thing that knows what it was trying to do. An integrator that "fixes" the clash itself is guessing at someone else's intent, and a wrong guess goes in silently. That is the story at the top of this article.

The health inspector: slow checks that never block the line

Some checks are slow: the full test suite, a complete build. A kitchen does not stop service so the inspector can walk through. A factory does not either. Slow checks run right after a change is saved, in the background, while the next change goes through the pass.

If they pass, the factory moves a bookmark called "last known good" up to this version. If they fail, it files a new task that names the exact change that caused the problem and hands it to the agent that wrote it. New work always starts from "last known good", so one bad change does not infect every task after it.

Why this is a good trade
The project might be broken for a few minutes. In exchange, nobody waits on a slow test run. And because changes went in one at a time, there is no detective work about who broke it. It was the last one through.

The second opinion: review, but only where it pays

After a change is saved, a different AI model can read it as a skeptic. But only for changes that touch sensitive areas, or that were rejected and retried along the way.

Why
Review is slow and expensive, and most changes are fine. A change that bounced twice is where the bugs live. Spend your most expensive attention there.

The scout: someone keeps the tickets coming

A factory with no tasks is a timer that does nothing. A scout is an agent whose only job is to keep the queue topped up. It looks where you tell it to, like failing tests or notes that say "fix this later", and writes new tasks. Each still needs a finish line that fails today, or it is turned away at the door.

The whole line, end to end

What you actually get out of it

Work that happens without you. The obvious benefit, and the reason anyone bothers. A small factory on a daily schedule can land a tested change every day for months. Kit's lands dozens.

Failure turns into work, not alarms. In most teams a broken build means a person stops what they are doing. In a factory it means a new task with an owner and a name attached. The system's own mistakes become one of its most reliable sources of work.

Rules that stick. Every time an agent makes the same mistake twice, you add one line to a check script. The factory gets stricter exactly where it was weak, and never forgets.

A complete paper trail. Every change traces back to a task, a finish line, a log of what the agent tried, and every check result. When something goes wrong three weeks later, you can see why it went in.

Your job changes. You stop deciding how to make each change, and spend your time on what should change next, which is the part that needed you all along.

What it costs

It is only as good as its checks. Tell an agent to make a weak test pass and it will make a weak test pass. Every shortcut in your checks becomes a shortcut in your code, made at machine speed.

The plumbing breaks in boring ways. When we built and tested our own small factory, the agents were rarely the problem. The bugs were in the scaffolding. Two agents fetching updates at the same instant tripped over each other. A script killed halfway through a merge left a mess that blocked everything after it. None of it glamorous. All of it would have stopped the factory overnight.

It will happily do busywork. Left alone, our scout proposed tasks like "add a test for this edge case." Its proof that each was needed: the test did not exist yet. Technically true, practically worthless. A factory optimizes for what you measure, so measure the right things.

It costs real money. Every agent run is billed. A scout, two builders and a reviewer running every few hours adds up.

Who is steering?

If agents write the tasks, build them, check them and fix them, it is fair to ask whether anyone decides where the project is going.

As far as anyone can tell from outside, yes, and it is a person. Nothing in Kit's diagram decides what to build. Every arrow that creates new work points back to an existing change: a failed check, a review finding, a collision. His other projects show where direction comes from. One is a tool for talking and drawing over his screen to hand ideas to an agent, which he describes as optimizing "the feedback loop between me + the robots." Another is a programming language he has given himself six months to move his company onto. Those are human decisions. The factory carries them out.

Warp's commercial factory product puts the human somewhere more visible. A lead agent, the "Factory Foreman", asks product questions, writes a plan, and waits for a person to approve it before any code is written. Afterwards a person still reviews the result.

The two disagree on one thing: whether a human approves each change before it goes in. Warp says yes. Kit says the checks are the approval. Both agree a human picks the direction. An agent that sets its own goals is possible, but it is the riskiest part to automate, for a simple reason.

A wrong direction passes every check.

How to set one up

You do not build Kit's factory on day one. His diagram is what a factory looks like at 50 changes a day. At one a day, most of it solves problems you do not have yet. Build in this order, and stop when the next step does not fix a problem you actually have.

1. Write the check first day one

One command that says yes or no about your project, and make your project pass it today. If you cannot trust this, nothing after it can be trusted either.

2. Write five tasks by hand day one

Each with a finish line a machine can run, and that fails today. If you cannot write the finish line, the task is too big. Make it smaller.

3. One agent, one task, by hand until one lands untouched

Give it its own copy of the project. Repeat until a task lands without you touching it. This is the minimum factory, and it already meets "one change a day".

4. Put it on a schedule once that works

Once a day is plenty to start. The schedule, not your attention, is what makes it a factory.

5. Move slow checks after landing when you notice waiting

Add the health inspector and the "last known good" bookmark once the full test suite is slow enough that you feel it.

6. Add a second agent, and the pass the moment there are two cooks

Two builders means changes can collide. That is when you need the integrator that takes turns.

7. Add the scout last, and give it a direction when the queue runs dry

Tell it what you are trying to achieve, not just where the loose ends are, or it will find you busywork forever.

Our version of all this, built and tested on a small project, is about 400 lines of shell script. It took six tasks from description to saved, tested and verified change, most in one to two minutes, including a collision it sorted out on its own. A separate script tests the factory itself, with a fake agent, in about 40 seconds. That matters more than it sounds. If you are going to trust a machine to change your code while you sleep, the machine needs tests too.

The new job

The pitch for AI coding was that you would write less code. The reality, for the people furthest along, is that you write different code. Less of the product, more of the process that produces it. The checks. The rules. The order things happen in.

And every morning, a few minutes reading the queue: closing tasks that are not worth doing, writing two that are, and looking at whatever got stuck overnight to see what it is trying to tell you.

The factory decides how. You still decide what. That turns out to be the job.
